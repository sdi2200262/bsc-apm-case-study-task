\section{Welcome}
\label{sec:welcome}

Thank you for taking part in this research. The study compares two AI-assisted software development frameworks, Agentic Project Management (APM) and GitHub Spec-kit, on a fixed coding task. Your contribution helps build the empirical evidence base for the thesis.

You are not being evaluated. The frameworks are. Whatever you produce during your sessions, including incomplete or non-functional code, is valuable data.

\subsection{Data privacy and anonymity}
\label{sec:privacy}

Submissions are handled with strict confidentiality. No personal identifier is linked to your data. You have been assigned a participant ID (e.g., \texttt{P001}); use it in your submission filenames as described later. AI interaction logs are encrypted with a key held only by the research team before being added to the published research dataset. The dataset's structure is transparent; the contents of your sessions remain private.

By proceeding, you consent to the anonymous collection and use of this data as described.

\subsection{Before you start}
\label{sec:beforestart}

You have been provided separately with:

\begin{itemize}
    \item your participant ID;
    \item your per-session framework assignment (which framework to use in session 1 and which in session 2);
    \item the Claude Code credentials you will use during the sessions, alongside short setup material describing how to apply them inside your Linux environment.
\end{itemize}

Keep these to hand. They do not appear anywhere in this guide or in the participant package.

Read the official documentation of your assigned framework before each session begins; a short throwaway run on an unrelated repository is recommended for first-time familiarity.

\begin{itemize}
    \item Agentic Project Management (APM): \url{https://agentic-project-management.dev}.
    \item GitHub Spec-kit: \url{https://github.github.io/spec-kit/}.
\end{itemize}

\section{Study overview}
\label{sec:overview}

\subsection{What you do}
\label{sec:whatyoudo}

You will complete the same coding task twice, in two separate three-hour sessions, each using a different framework. The two sessions can run back to back, on the same day, or on different days. They must not overlap, and you must approach the second session as if the first had not happened, working from a fresh checkout of the codebase.

\subsection{Time}
\label{sec:time}

Each session is strictly time-boxed to three hours. Stop at the three-hour mark whether or not the task is complete. Submitting unfinished work is an expected and valid outcome.

\subsection{What you submit}
\label{sec:whatyousubmit}

After each session you produce one zip file containing two artefacts at its root:

\begin{itemize}
    \item \texttt{solution.patch}: a unified diff of your work against a pinned starting commit of the implementation codebase.
    \item \texttt{transcripts/}: the AI interaction logs. One \texttt{.jsonl} per main session at the top level, plus a subdirectory of the same uuid for each carrying the \texttt{subagents/} and \texttt{tool-results/} records Claude Code wrote alongside that session.
\end{itemize}

The zip filename follows the strict pattern \texttt{\{PID\}\_S\{1\textbar{}2\}\_\{apm\textbar{}speckit\}.zip}, e.g., \texttt{P001\_S1\_apm.zip}.

You also answer a short post-session questionnaire about your experience with the framework. The questionnaire and the zip go through a single submission form, whose URL is given later in Section~\ref{sec:wrapping}, step 5.

\section{Participant package}
\label{sec:package}

This guide ships inside a participant-package zip alongside the task specification and a helper skill that drives the participant's setup and per-session lifecycle. Its layout:

\begin{verbatim}
participant-package/
|-- participant-guide-cc.pdf       # this document
|-- task/
|   |-- PRD.md                     # Product Requirements Document
|   `-- PROMPT.md                  # default opening prompt for the AI
`-- .claude/
    `-- skills/
        `-- bsc-apm-study-helper/  # Claude Code skill (see Section 3.1)
            |-- SKILL.md
            `-- references/...
\end{verbatim}

\texttt{PRD.md} is the sole source of truth for what to implement.

\subsection{AI-assisted setup}
\label{sec:aiassist}

The package also ships a Claude Code skill at \texttt{.claude/skills/bsc-apm-study-helper/} as an alternative to the hands-on instructions in the rest of this guide. The skill drives setup, the per-session lifecycle, the between-sessions reset, and the optional cleanup, asking for your confirmation before running anything. Two ways to use it:

\textbf{From your host machine, with your AI assistant.} Whatever AI assistant you have on your host, it can access the skill as plain markdown after the package is unzipped, and walk you through host-side setup, including launching a Linux VM. The study coordinator's invitation includes a starter prompt you can paste into your AI assistant to get started; it fetches and unzips the package, reads the skill, and continues from there.

\textbf{From inside the Linux environment, with Claude Code installed.} Fetch and unzip the package inside the Linux environment, open Claude Code with the participant-package directory as its working directory, and the skill loads natively.

The skill then drives the rest of the work in conversation with you, guiding you through this setup.

Both paths land on the same workspace and produce the same submission. The hands-on instructions in the rest of this guide cover every operation the skill walks through; choose whichever you prefer.

\note{The skill is project-scoped to the participant-package directory, not user-level. It is therefore not loaded in your task's workspace, only in a Claude Code session opened from the participant-package directory. Do not copy it to \texttt{\textasciitilde/.claude/skills/} or to your workspace's \texttt{.claude/skills/}; doing so would defeat that isolation.}

\warn{The skill is for logistics only. It is instructed to refuse questions about the implementation task or the frameworks themselves and to redirect you to their documentation, but the agent may still slip; if it does, the responsibility to disregard such answers lies with you. Acting on, paraphrasing, or carrying any task or framework content the helper produced into a session contaminates your study data.}

\section{System requirements}
\label{sec:requirements}

\subsection{Operating system}
\label{sec:os}

The study runs inside a dedicated Linux virtual machine, freshly created for the study. The tool depends on your host operating system: Lima on macOS and on native Linux; WSL2 with a new Ubuntu distribution on Windows.

\note{Create a new VM for the study; do not reuse a pre-existing VM or WSL distribution you use for other work. Prior Claude Code state, project history, or partial setups would interfere with transcript collection and authentication, and the post-session evaluation depends on a clean baseline.}

\textbf{macOS and native Linux:} Use Lima (\url{https://lima-vm.io}). A free, open-source, CLI-driven VM manager that brings up an Ubuntu LTS VM in one command. Install Lima following the official instructions at \url{https://lima-vm.io/docs/installation/}, which cover Homebrew on macOS and distribution packages or release tarballs on Linux. Then:

\begin{verbatim}
limactl start --name=task --cpus=4 --memory=8 --disk=20 \
    --tty=false template:ubuntu-24.04
limactl shell task
\end{verbatim}

\texttt{limactl shell task} opens a shell inside the VM but lands you at the host directory you launched it from, not the VM's own home; \texttt{cd \textasciitilde} before any download or extraction so files land on the VM filesystem.

\textbf{Windows:} Use WSL2 (\url{https://learn.microsoft.com/en-us/windows/wsl/}). Install WSL2 following the official Microsoft instructions at \url{https://learn.microsoft.com/en-us/windows/wsl/install}. Then, from an elevated PowerShell on the Windows host, create the \texttt{task} distribution from the official Ubuntu rootfs tarball and launch it:

\begin{verbatim}
$rootfs = "ubuntu-noble.tar.gz"
$url = "https://cloud-images.ubuntu.com/wsl/noble/current/" +
       "ubuntu-noble-wsl-amd64-wsl.rootfs.tar.gz"
Invoke-WebRequest -Uri $url -OutFile $rootfs
mkdir C:\WSL -Force | Out-Null
wsl --import task C:\WSL\task $rootfs
wsl -d task
\end{verbatim}

The first shell lands you in as \texttt{root} (the imported rootfs has no non-root user yet); operating as \texttt{root} is fine for the rest of the study, and sudo-prefixed commands in later sections work as expected under root.

\warn{Docker Desktop is not a substitute. The mock environment described in Section~\ref{sec:env} runs Docker Engine \emph{inside} the VM, not on the host.}

\subsection{System resources}
\label{sec:resources}

The Linux environment needs at least 4 vCPUs, 8 GB of RAM, and a 20 GB virtual disk; the launch commands above provision these for VM users. After Docker images are loaded (about 1.6 GB for the openeclass container), at least 5 GB of free disk should remain for the workspace, Docker state, and transient files.

\subsection{Tools and libraries}
\label{sec:tools}

The case-study work needs a container runtime (Docker Engine with Compose v2), a C build chain (\texttt{gcc}, \texttt{make}, \texttt{valgrind}, \texttt{pkg-config}, plus the \texttt{libcurl} and \texttt{libxml2} development headers), two scripting runtimes (Python 3.10 or newer with \texttt{uv}, and Node.js with \texttt{npm}), and a handful of command-line utilities (\texttt{git}, \texttt{curl}, \texttt{tar}, \texttt{zip}, \texttt{unzip}, \texttt{openssl}, \texttt{bash} 3.2 or newer, and \texttt{gh}). Install Docker first via the official convenience script. Download it before running so you can read it:

\begin{verbatim}
curl -fsSL https://get.docker.com -o /tmp/install-docker.sh
sudo sh /tmp/install-docker.sh
sudo usermod -aG docker $USER
\end{verbatim}

The new \texttt{docker} group membership takes effect on your next login or after \texttt{newgrp docker}. Install everything else with \texttt{apt} and the official \texttt{uv} installer:

\begin{verbatim}
sudo apt-get update
sudo apt-get install -y \
    build-essential pkg-config valgrind \
    libcurl4-openssl-dev libxml2-dev \
    git curl tar zip unzip openssl gh python3 python3-pip npm
curl -LsSf https://astral.sh/uv/install.sh -o /tmp/install-uv.sh
sh /tmp/install-uv.sh
\end{verbatim}

If \texttt{uv --version} reports \texttt{command not found} immediately after the install, run \texttt{source \textasciitilde/.local/bin/env} once or open a new login shell so the installer's PATH update takes effect. The C minimums are \texttt{gcc} 9.0 (for C11), \texttt{libcurl} 7.81.0, and \texttt{libxml2} 2.9.13; Ubuntu 22.04 and 24.04 both satisfy them. Verify the toolchain:

\begin{verbatim}
gcc --version
pkg-config --modversion libcurl
pkg-config --modversion libxml-2.0
valgrind --version
python3 --version
node --version
npm --version
uv --version
\end{verbatim}

\section{AI tools}
\label{sec:aitools}

The session uses a coding-agent CLI (Claude Code) and one of two AI-assisted development frameworks (APM or Spec-kit). The participant package does not bundle any of them. Install Claude Code once before either session; the two framework subsections below cover their own install models (APM ships as a global npm package; Spec-kit is invoked via \texttt{uvx} from a release tag on every call, with no persistent install needed). Set up whichever framework is assigned to your current session before that session begins. The system requirements in Section~\ref{sec:requirements} cover the underlying tools all three depend on.

\subsection{Claude Code}
\label{sec:aitools:claude}

The recommended install path is Anthropic's shell installer:

\begin{verbatim}
curl -fsSL https://claude.ai/install.sh -o /tmp/install-cc.sh
bash /tmp/install-cc.sh
claude --version
\end{verbatim}

Claude Code \texttt{2.1.126} is the floor verified for the study; anything newer is fine.

The official instructions at \url{https://docs.claude.com/en/docs/claude-code} cover other install paths. Authentication itself runs once, inside this Linux environment; follow the setup material the study coordinator gave you separately (see Section~\ref{sec:beforestart}) to apply it. The credentials and the setup material live inside this VM from that point on; do not reuse them elsewhere.

\subsection{Agentic Project Management (APM)}
\label{sec:aitools:apm}

APM ships as an npm package; the CLI is invoked as \texttt{apm}.

\begin{verbatim}
sudo npm install -g agentic-pm
apm --version
\end{verbatim}

\subsection{GitHub Spec-kit}
\label{sec:aitools:speckit}

Spec-kit runs through \texttt{uvx} from a release tag of the upstream repository; the CLI is invoked as \texttt{specify}, prefixed by the same \texttt{uvx --from} expression on every invocation. The study does not pin a specific tag: open \url{https://github.com/github/spec-kit/releases}, pick the current release, and use that tag for every Spec-kit command in your session. \texttt{v0.8.5} is the floor verified for the study; anything newer is fine.

\begin{verbatim}
uvx --from git+https://github.com/github/spec-kit.git@<tag> \
    specify --help
\end{verbatim}

\section{Workspace}
\label{sec:workspace}

The participant package's \texttt{task/} directory holds \texttt{PRD.md} (the requirements you implement against) and \texttt{PROMPT.md} (the message you give the AI to open the session). The \emph{workspace} is the directory inside your Linux VM in which you open Claude Code; it is the AI's working directory for the session, and it must end up with this exact layout:

\begin{verbatim}
<workspace>/
|-- PRD.md
|-- PROMPT.md
|-- eclass-mcp-server/      # implementation codebase
`-- openeclass/             # legacy PHP codebase (read-only reference)
\end{verbatim}

Create the workspace as a fresh directory of your choice on the Linux filesystem (\texttt{\textasciitilde/workspace/} is a reasonable default), copy \texttt{PRD.md} and \texttt{PROMPT.md} into it from the participant package's \texttt{task/} directory, and clone the two repositories alongside them following the next subsection.

\subsection{Cloning the codebases}
\label{sec:cloning}

Clone \texttt{eclass-mcp-server} and check out the pinned commit \texttt{dbd2d16}. This commit is the patch baseline: every diff you submit is computed against it.

\begin{verbatim}
cd <workspace>
git clone https://github.com/sdi2200262/eclass-mcp-server.git
cd eclass-mcp-server
git checkout dbd2d16
uv sync --dev --all-extras
cd ..
\end{verbatim}

Clone \texttt{openeclass} at its pinned commit \texttt{e8b3329}. The AI treats this codebase as a read-only reference; you should not modify it.

\begin{verbatim}
cd <workspace>
git clone https://github.com/gunet/openeclass.git
cd openeclass
git checkout e8b3329
cd ..
\end{verbatim}

\section{Mock environment}
\label{sec:env}

The task integrates with openeclass through a single-sign-on flow, both for the existing Python MCP (Model Context Protocol) server it expands and for the C replica it asks for. The study ships a self-contained \emph{mock environment} that you run locally during each session: a real openeclass instance paired with a mock SSO service whose flow matches \texttt{eclass-mcp-server}'s integration, pre-loaded with a fixed test data set so every participant's session runs against identical state. The openeclass instance inside this mock is the same release the read-only \texttt{openeclass/} checkout in your workspace points at, packaged as a docker image; reading the \texttt{openeclass/} tree is the most direct way to understand how the live mock behaves.

\subsection{Download and install}
\label{sec:env:install}

The mock environment ships from the \texttt{sdi2200262/bsc-apm-case-study-task} GitHub repository as two architecture-specific releases, each with a single tarball asset:

\begin{itemize}
    \item Tag \texttt{bsc-apm-case-study-task} ships \texttt{bsc-apm-amd64.tar.gz} for x86\_64 hosts (most Intel and AMD Linux machines, and the Linux VM on an Intel Mac).
    \item Tag \texttt{bsc-apm-case-study-task-arm64} ships \texttt{bsc-apm-arm64.tar.gz} for arm64 hosts (Apple Silicon Macs running a Linux VM, arm64 Linux servers, Raspberry Pi 4/5, etc.).
\end{itemize}

Identify your architecture with \texttt{uname -m}: \texttt{x86\_64} means amd64, \texttt{aarch64} or \texttt{arm64} means arm64. Pick a prefix on disk for the mock environment, separate from your workspace (the rest of this guide writes \texttt{<mock>/} for that path; \texttt{\textasciitilde/.bsc-apm} is a reasonable default). Run \emph{one} of the two download commands below, the one that matches your architecture:

\begin{verbatim}
mkdir -p <mock> && cd <mock>

# x86_64 hosts:
curl -L -o bsc-apm-amd64.tar.gz \
    https://github.com/sdi2200262/bsc-apm-case-study-task/releases/\
download/bsc-apm-case-study-task/bsc-apm-amd64.tar.gz

# arm64 hosts:
curl -L -o bsc-apm-arm64.tar.gz \
    https://github.com/sdi2200262/bsc-apm-case-study-task/releases/\
download/bsc-apm-case-study-task-arm64/bsc-apm-arm64.tar.gz
\end{verbatim}

Then unpack and bring the stack up. \texttt{./install} loads the bundled Docker images, generates self-signed TLS certificates into \texttt{./certs/}, and writes a pre-configured \texttt{.env} alongside. \texttt{./scripts/up} brings the three containers up, performs openeclass's first-time install on first run, and applies the test data; this takes a few minutes on a clean host.

\begin{verbatim}
tar -xzf bsc-apm-*.tar.gz
./install
./scripts/up
\end{verbatim}

The stack listens on two URLs once it is ready:

\begin{itemize}
    \item \texttt{http://localhost/} for the openeclass instance.
    \item \texttt{https://localhost:18443/} for the mock authentication service.
\end{itemize}

Ports 80 and 18443 must be free on the Linux environment. Port 80 is the default HTTP port and is more commonly held by another service than 18443 is; if either is bound, stop the holder before running \texttt{./scripts/up}. The helper skill walks through identifying and stopping the holder if needed.

\subsection{Lifecycle commands}
\label{sec:env:lifecycle}

Once installed, manage the environment from its prefix:

\begin{itemize}
    \item \texttt{./scripts/up}: bring the stack up. Idempotent.
    \item \texttt{./scripts/down}: stop the stack; named volumes survive.
    \item \texttt{./scripts/status}: probe each service from the mock side and report whether the stack itself is healthy.
    \item \texttt{./scripts/verify-mcp -{}-mcp-root <path>}: consumer-side complement to \texttt{status}; verifies that an \texttt{eclass-mcp-server} checkout authenticates against the mock with the \texttt{.env} and \texttt{certs/} it has been given. Runs only against the pinned baseline (Section~\ref{sec:cloning}), at initial setup or after a between-sessions reset.
    \item \texttt{./scripts/logs}: tail container logs.
    \item \texttt{./scripts/reset}: drop database state and re-apply the test data.
\end{itemize}

You should not need to reset during a session. If you do (for instance, after a destructive experiment from the AI), \texttt{./scripts/reset} returns the environment to its initial state.

\subsection{MCP server configuration}
\label{sec:env:config}

The \texttt{.env} and \texttt{certs/} that \texttt{./install} wrote are everything the implementation needs to authenticate against the mock. Copy both into the \texttt{eclass-mcp-server/} checkout, preserving the \texttt{certs/} subdirectory:

\begin{verbatim}
cp <mock>/.env <workspace>/eclass-mcp-server/.env
cp -r <mock>/certs <workspace>/eclass-mcp-server/certs
\end{verbatim}

The \texttt{.env} references the certificate by relative path, so no further configuration is required. After the copy, run \texttt{<mock>/scripts/verify-mcp -{}-mcp-root <workspace>/eclass-mcp-server} (Section~\ref{sec:env:lifecycle}) to confirm the wiring; it prints \texttt{wiring ok} on success.

\subsection{Uninstall}
\label{sec:env:uninstall}

To remove the mock environment from your machine after the study, stop the stack and drop its volumes (\texttt{down -v}), remove the loaded images, and delete the prefix:

\begin{verbatim}
docker compose -f <mock>/compose.yaml down -v
docker rmi bsc-apm/openeclass:dev bsc-apm/mock-cas:dev
rm -rf <mock>
\end{verbatim}

\section{Session workflow}
\label{sec:workflow}

A session has three phases: starting, working, and wrapping up. Between your two sessions, run the reset at the end of this section to return the workspace and the transcript store to the same state the setup steps above produced for session 1.

\subsection{Starting a session}
\label{sec:starting}

The session begins the moment you send your first message in the workspace Claude Code session; that timestamp is your wall-clock start time, not the moment you launch \texttt{claude}. Inside the workspace, run your assigned framework's workspace bootstrap (\texttt{apm init} for APM; \texttt{uvx --from git+https://github.com/github/spec-kit.git@<tag> specify init --here} for Spec-kit, using the same \texttt{<tag>} picked at install time), launch Claude Code, and send the framework's first message per its official documentation (Section~\ref{sec:beforestart}).

\subsection{Working on the task}
\label{sec:working}

Work for up to three hours and stop at the three-hour mark whether or not you have finished. Use only the framework assigned to your current session and follow its documented workflow as written; the study compares frameworks as documented, not as adapted on the fly. The mock environment running locally is the same surface the post-session evaluation runs against, so testing your implementation against it as you go is the most direct way to check it against the PRD. Do not delete any \texttt{.jsonl} file from your workspace's transcript directory; those are your transcripts and are needed in your submission.

\subsection{Wrapping up}
\label{sec:wrapping}

\textbf{1. Create the patch.} From inside the implementation codebase, stage every change (including new files) and diff against the pinned commit. The \texttt{-{}-cached} flag is what pulls newly created source files into the diff, even when the working tree is otherwise clean.

\begin{verbatim}
cd <workspace>/eclass-mcp-server
git add -A
git diff --cached dbd2d16 > ../solution.patch
\end{verbatim}

\textbf{2. Collect the transcripts.} Claude Code stores transcripts under \texttt{\textasciitilde/.claude/projects/} in a per-workspace subdirectory whose name is the workspace's absolute path with every character that is not an ASCII letter, digit, or hyphen replaced by \texttt{-}. The path separator \texttt{/}, the dot \texttt{.}, and the underscore \texttt{\_} all get replaced; usernames or directory names containing those characters are normalised the same way. List the entries and identify the directory belonging to your workspace by substring overlap with the workspace path:

\begin{verbatim}
ls ~/.claude/projects/
\end{verbatim}

Inside that directory, the \texttt{.jsonl} files are your transcripts; the first record's \texttt{timestamp} field is the session's start, the last record's is its end. Pick the transcripts whose first timestamp falls inside the session window:

\begin{verbatim}
ls -la ~/.claude/projects/<encoded>/*.jsonl
head -1 ~/.claude/projects/<encoded>/<sessionId>.jsonl
tail -1 ~/.claude/projects/<encoded>/<sessionId>.jsonl
\end{verbatim}

For each matching transcript, copy the \texttt{.jsonl} and the sibling per-session subdirectory of the same uuid (carrying the \texttt{subagents/} and \texttt{tool-results/} records) into \texttt{<workspace>/transcripts/}. Sessions that did not dispatch any subagents have no such subdirectory; copy only the \texttt{.jsonl} for those, and that is the correct shape:

\begin{verbatim}
mkdir -p <workspace>/transcripts
cp ~/.claude/projects/<encoded>/<sessionId>.jsonl \
    <workspace>/transcripts/
cp -r ~/.claude/projects/<encoded>/<sessionId>/ \
    <workspace>/transcripts/<sessionId>/
\end{verbatim}

The third command runs only when \texttt{\textasciitilde/.claude/projects/<encoded>/<sessionId>/} exists; check with \texttt{ls -d \textasciitilde/.claude/projects/<encoded>/<sessionId>/} first. Repeat for every transcript that belongs to the session, then verify:

\begin{verbatim}
ls -la <workspace>/transcripts
\end{verbatim}

The directory should contain one \texttt{<sessionId>.jsonl} per main session and, optionally, one \texttt{<sessionId>/} subdirectory per session that dispatched subagents.

\textbf{3. Package the submission.} Zip \texttt{solution.patch} and \texttt{transcripts/} together at the workspace root. The filename uses your participant ID, the session number, and the framework you used in this session:

\begin{verbatim}
cd <workspace>
zip -r P001_S1_apm.zip solution.patch transcripts/

\subsection{Resetting between sessions}
\label{sec:between}

Run this after the first session has wrapped up and before the second session starts. Before running any of the steps below, confirm that session 1's submission zip is in your safe-storage directory (e.g., \texttt{ls -la \textasciitilde/Documents/bsc-apm-submissions/} should list \texttt{P001\_S1\_*.zip}); the reset is destructive and only zips outside the workspace survive. The reset then returns the workspace and the transcript store to the same state the setup steps above produced for session 1, so session 2 begins from an identical baseline. The mock environment is left alone unless you have a reason to believe it has drifted from its initial state.

\textbf{1. Reset the implementation codebase.} From inside \texttt{eclass-mcp-server}, hard-reset to the pinned commit, wipe untracked and ignored files, and rebuild the virtual environment from scratch:

\begin{verbatim}
cd <workspace>/eclass-mcp-server
git reset --hard dbd2d16
git clean -fdx
uv sync --dev --all-extras
\end{verbatim}

\texttt{git clean -fdx} removes every untracked file, including ignored files such as \texttt{.venv/} and any \texttt{\_\_pycache\_\_/} directories. Re-copy \texttt{.env} and \texttt{certs/} from the mock-environment prefix afterwards (Section~\ref{sec:env:config}); they are removed by \texttt{git clean}.

\textbf{2. Reset the reference codebase.} Do the same for \texttt{openeclass}, in case the AI inadvertently modified it:

\begin{verbatim}
cd <workspace>/openeclass
git reset --hard e8b3329
git clean -fdx
\end{verbatim}

\textbf{3. Sweep the workspace.} Confirm the workspace root contains exactly four entries: \texttt{PRD.md}, \texttt{PROMPT.md}, \texttt{eclass-mcp-server/}, and \texttt{openeclass/}.

\begin{verbatim}
ls -la <workspace>
\end{verbatim}

Delete any extra files or directories the AI may have created at the workspace root. If \texttt{PRD.md} or \texttt{PROMPT.md} were modified during the session, restore them from the participant package's \texttt{task/} directory; session 2 must read them in their original form.

\textbf{4. Wipe the Claude Code project state.} Remove this workspace's entry under \texttt{\textasciitilde/.claude/projects/} so session 2 starts from a clean baseline. The directory contains transcripts, per-session subdirectories, the project-local \texttt{memory/} store, and anything else Claude Code has cached for this workspace; the deletion is permanent.

\begin{verbatim}
ls -la ~/.claude/projects/<encoded>/
rm -rf ~/.claude/projects/<encoded>/
\end{verbatim}

The \texttt{ls} step is the inventory; review it before running \texttt{rm}. Run only after you have safely stored the session's zip. Claude Code recreates the project directory on the next launch.

\textbf{5. Reset the mock environment, only if needed.} The mock environment retains its initial state across sessions and usually does not need a reset. Reset it only if a previous session modified the test data:

\begin{verbatim}
cd <mock>
./scripts/reset
\end{verbatim}

\textbf{6. Confirm the baseline.} After the reset, confirm the workspace and the transcript store match the same state setup produced for session 1:

\begin{itemize}
    \item \texttt{<mock>/scripts/status} reports every service ok.
    \item \texttt{<workspace>/eclass-mcp-server} is at \texttt{dbd2d16} with a clean working tree.
    \item \texttt{<workspace>/openeclass} is at \texttt{e8b3329} with a clean working tree.
    \item The workspace root contains \texttt{PRD.md}, \texttt{PROMPT.md}, \texttt{eclass-mcp-server/}, and \texttt{openeclass/}, and nothing else; \texttt{PRD.md} and \texttt{PROMPT.md} match their original contents from the participant package.
    \item Your workspace's project directory under \texttt{\textasciitilde/.claude/projects/} holds no session-1 state.
\end{itemize}

Once the baseline is in place, return to Section~\ref{sec:starting} and repeat the same starting-working-wrapping-up flow for session 2 (with your other assigned framework). Session 2 ends after Section~\ref{sec:wrapping}, step 5 (\emph{Submit the form}); the resetting steps are not needed to be run again.
